# Архитектура обмена данными Java ↔ FSO оптическая рация

## Контекст

**Что строим:** надёжный протокол прикладного уровня для оптической рации.

**Топология:**
```
[Java PC/Android] ←USB CDC→ [STM32F722 — чёрный ящик, НЕ меняем]
                                      ↕ FSO (~24 кбит/с, потери <5%)
[Java PC/Android] ←USB CDC→ [STM32F722 — чёрный ящик, НЕ меняем]
```

**Что делает STM32 (неизменяемо):**
- Фрагментирует входящий байтовый поток в физические кадры ≤ 255 байт
- Добавляет свой CRC к каждому кадру — плохие кадры молча отбрасываются
- Выдаёт прошедшие CRC кадры в виде байтового потока на другой стороне

**Для Java — прозрачный COM-порт. Но потери кадров (< 5%) = тихие пропуски в байтовом потоке.**

**Вся протокольная логика — только в Java (оба конца).**

---

**Параметры канала:**
| Параметр | Значение |
|---|---|
| Эффективная скорость | ~24 кбит/с ≈ 3000 байт/с |
| Физический кадр STM32 | ≤ 255 байт (CRC добавляет MCU) |
| Round-trip PING | 120–130 мс |
| Потери кадров (< 2 км) | **< 5%** |
| Дополнительный CRC на прикл. уровне | нужен (CRC MCU не виден Java) |
| Flow control аппаратный | нет (нет RTS/CTS) |
| Трафик | смешанный: текст, файлы, голосовые сообщения |
| Направление | двусторонний, оба равнозначны |

## Аспект 1. Framing / Инкапсуляция

**Проблема:** STM32 выдаёт непрерывный байтовый поток. При потере физического кадра (< 5%) в потоке пропадает кусок ≤ 255 байт. Java не знает где границы application-пакетов. Нужно быстро восстановить синхронизацию.

### Вариант A — Length-delimited + маркер SOF ⚡ рекомендуется при потерях < 5%

```
[SOF: 0x7E] [SEQ: 1B] [FLAGS: 1B] [LEN: 1B] [PAYLOAD ≤ 250B] [CRC8: 2B]
```
- Overhead: 6 байт (2.4% при 250-байтном payload)
- Sync recovery: при потере кадра читаем LEN байт → CRC плохой → ищем следующий 0x7E
- При < 5% потерях recovery происходит редко → простота важнее, чем скорость recovery
- Сложность Java: минимальная (scan for SOF → read length → check CRC)
- CRC8 (vs CRC8): дополнительная защита от битовых ошибок, не только потерь
- **Предпочтителен:** при потерях < 5%, низкой частоте ресинхронизации

### Вариант B — Byte stuffing (стиль PtPP2)

```
[0x7D] [SEQ + PAYLOAD, стаффинг] [CRC8] [0x7D]
```
- Overhead: 2–4% + возможное удвоение при binary data
- Sync recovery: немедленная (0x7D = граница кадра всегда)
- Максимальный payload в 255-байтном окне: ~125–245 байт (зависит от данных)
- **Предпочтителен:** при частых потерях (> 10%) или нужна мгновенная ресинхронизация

### Вариант C — COBS

```
[overhead_byte] [payload, 0x00 eliminated] [0x00]
```
- Overhead: 1 байт на 254 байта (< 0.5%)
- 254 байта полезной нагрузки в физическом кадре 255 байт
- Sync recovery: по разделителю 0x00
- Сложность: нужна отдельная Java и C реализация COBS
- **Предпочтителен:** если критичен каждый байт канала (у нас запас есть)

### Итог: Аспект 1

| | A (Length+SOF) | B (Byte stuffing) | C (COBS) |
|---|---|---|---|
| Overhead | 2.4% | 2–4% | < 0.5% |
| Sync recovery | ~1 RTT | мгновенно | мгновенно |
| Max payload/кадр | 250 B | ~125–245 B | 254 B |
| Сложность Java | ⭐ минимальная | низкая | средняя |
| При потерях < 5% | ✅ оптимален | избыточно | оверинжиниринг |

**Выбор: Вариант A.** При потерях < 5% скорость ресинхронизации не критична. Простота важнее.

## Аспект 2. Формат NACK и управление сессией

**Нумерация:** SEQ 8-бит (0–255). При скорости 3000 байт/с и кадре 250 байт → ~12 кадров/с. Окно 8 → обёртка за ~20 секунд — допустимо.

### Вариант A — Bitmap ACK ⚡ рекомендуется

```
[TYPE: ACK=0x01] [WINDOW_BASE: 1B] [BITMAP: 2B]
Итого: 4 байта
```
Каждый бит = один пакет в окне. 2 байта = 16-пакетное окно.
Бит 1 = получен, 0 = потерян.

- При < 5% потерях в окне 8: обычно 0–1 нулевых бита → пересылка 0–1 пакета
- Фиксированный размер, легко парсится
- Java: `(bitmap >> seq) & 1` → решение о переотправке

### Вариант B — List NACK (список потерянных)

```
[TYPE: NACK=0x02] [COUNT: 1B] [SEQ1, SEQ2, ...]
Итого: 2 + n байт
```
- При < 5% потерях: типично 0–1 потерянных → 2–3 байта
- Чуть меньше при единичных потерях, чуть больше при пакетных
- Чуть сложнее парсинг (переменный размер)

### Вариант C — Cumulative ACK (TCP-стиль)

```
[TYPE: ACK] [LAST_IN_ORDER: 1B]
Итого: 2 байта
```
- Самый компактный
- При потере пакета N — все > N ждут досылки → head-of-line blocking
- При < 5% потерях эффект небольшой, но идеология неудобна для файлов

### Обработка потери NACK / таймаута

```
Таймер ожидания ACK = 3 × RTT ≈ 400 мс  (редко срабатывает при <5% потерях)

Таймаут → отправить PROBE (2 байта): «каков твой WINDOW_BASE + bitmap?»
PROBE без ответа × 3 = сессия закрыта

При потере NACK (редко при < 5%):
  → таймер отправителя истёк → переотправить всё окно
  → получатель применяет deduplicate по SEQ (идемпотентно)
```

**Выбор: Вариант A (Bitmap ACK).** Фиксированный размер. При < 5% потерях overhead и сложность минимальны.

## Аспект 3. Размер окна / Batch size

**Расчёт:**
```
BDP = 3000 байт/с × 0.125 с = 375 байт ≈ 1.5 кадра по 250 байт
```
Теоретический минимум окна для насыщения канала: **2 кадра**.
При < 5% потерях запас нужен небольшой.

### Вариант A — n = 4 ⚡ рекомендуется

- RAM (Java): 4 × 255 = 1 KB для retransmission buffer
- При < 5% потерях: в среднем 0.2 кадра переотправки → ~1% overhead
- Задержка (text messages): ~1.3 RTT ≈ 170 мс для 4-кадрового окна
- Достаточно для насыщения канала + небольшой запас

### Вариант B — n = 8

- RAM: 8 × 255 = 2 KB
- Лучше для file transfer (меньше пауз)
- При < 5% потерях: практически нет разницы с n = 4
- Выбрать если файлы > 50 KB частые

### Вариант C — Адаптивное n = 2..16

- Начинает с 2, растёт с каждым успешным ACK
- Оптимально в теории, но: лишняя сложность, JVM scheduler вносит джиттер
- При < 5% потерях выигрыш незначителен

### Итог по Аспекту 3

| | n = 4 | n = 8 | Adaptive |
|---|---|---|---|
| RAM retransmit buffer | 1 KB | 2 KB | до 4 KB |
| Пропускная способность | ≈ насыщение | > насыщение | оптимум |
| Простота | ⭐ | средняя | сложно |
| При < 5% потерях | ✅ оптимален | избыточно | оверинжиниринг |

**Выбор: n = 4** для текстовых сообщений и голосовых. **n = 8** только если файлы > 50 KB — и это можно сделать параметром сессии.

## Аспект 4. Буферизация и Flow Control

**Проблема:** Java не должна отправлять данные быстрее, чем FSO канал (3000 байт/с). Без hardware flow control (нет RTS/CTS) — переполнение буфера STM32.

### Вариант A — Credit-based (ACK-driven pacing) ⚡ рекомендуется

```
Sender Java:
  credits = window_size (= 4)
  while (hasData) {
      waitForCredit()      // блокирует, если credits = 0
      sendFrame()
      credits--
  }

При получении ACK:
  credits += acked_count  // восстановить слоты
  signal(waitForCredit)
```

- Java: `LinkedBlockingQueue` + `Semaphore(window_size)`
- Нет busy-wait, нет sleep
- Естественный backpressure
- Throughput: максимально используем полосу при хорошем канале

### Вариант B — Rate limiter (токенное ведро)

```java
RateLimiter limiter = RateLimiter.create(3000.0); // bytes/sec
// перед каждой отправкой: limiter.acquire(frameSize)
```

- Простой (Guava RateLimiter — одна строка)
- Не реагирует на состояние канала (ACK/NACK)
- При потерях: продолжает слать, не ждёт подтверждений
- **Приемлем** только как дополнительный ограничитель поверх Варианта A

### Вариант C — Explicit XON/XOFF через application-level PAUSE

```
MCU → Java: PAUSE frame (когда буфер > 75%)
MCU → Java: RESUME frame (когда буфер < 25%)
```

- Работает, но STM32 у нас **неизменяемый** → нельзя добавить PAUSE/RESUME
- ❌ Не применимо в нашем случае

### Итог по Аспекту 4

| | A (Credit-based) | B (Rate limiter) | C (XON/XOFF) |
|---|---|---|---|
| Точность | ⭐ динамическая | статичная | точная |
| Изменения STM32 | нет | нет | ❌ нужны |
| Реализация Java | Semaphore | RateLimiter | недоступно |
| Перегрузка MCU | нет | возможна при потерях | нет |

**Выбор: Вариант A.** Credit-based семафор в Java — 15 строк кода, никаких изменений в STM32.

## Аспект 5. Тестирование без железа

### Вариант A — Java FSO Channel Emulator (unit-тесты) ⚡ рекомендуется в первую очередь

```java
class FSOChannelEmulator implements AutoCloseable {
    // Параметры канала
    double lossRate   = 0.05;  // 5%
    int    delayMs    = 130;   // RTT/2
    int    jitterMs   = 20;    // случайный джиттер
    int    burstSize  = 1;     // потери одиночные или burst
    Random rng        = new Random(42); // seed → детерминизм

    // Подключается вместо реального COM-порта
    // реализует InputStream/OutputStream
}
```
Сценарии для тестов:
- `lossRate=0.05` — базовый канал
- `lossRate=0.20` — деградация канала (дальняя дистанция)  
- `burstSize=3` — пакетные потери (атмосферные флуктуации)
- `jitterMs=500` — экстремальный джиттер

Покрывает: потерю DATA, потерю ACK, timeout, пакетные потери, дублирование (при ретрансмиссии).

### Вариант B — Virtual COM pair (интеграционные тесты)

**Windows:** com0com создаёт пару `COM3 ↔ COM4`  
**Linux:** `socat PTY,link=/dev/ttyV0 PTY,link=/dev/ttyV1`

Прокси между ними вставляет задержки и потери, два экземпляра Java общаются.
- Тестирует: реальный serial port driver, USB CDC timing, Java threading
- Медленнее итерации, но ближе к реальности

### Вариант C — STM32 + software injector (hardware тест)

Финальная верификация: два реальных STM32, физическое соединение. Программный injector потерь на MCU (изменять нельзя, значит — через прокси на Java, имитируя «плохой кабель»). Либо просто тестировать на реальном FSO-оборудовании.

### Итог по Аспекту 5

| | A (Emulator) | B (Virtual COM) | C (Hardware) |
|---|---|---|---|
| Скорость итерации | ⭐ | средняя | медленно |
| Детерминизм | ⭐ (seed) | нет | нет |
| Покрытие USB/serial | нет | ✅ | ✅ |
| Нужно железо | нет | нет | ✅ |

**Порядок:** A → B → C. Большинство багов поймать на A.

## Ответы на уточняющие вопросы

### Как подтверждается получение пакета — пошагово

```
PC-A отправляет: SEQ=0  SEQ=1  SEQ=2  SEQ=3   (окно 4)
                  ↓      ✗      ↓      ↓        (SEQ=1 потерян на FSO)

PC-B получает:   0      —      2      3
PC-B отправляет: ACK  WINDOW_BASE=0  BITMAP=0b1101
                      ↑ бит 0=1(получен), бит 1=0(потерян), бит 2=1, бит 3=1

PC-A читает bitmap: бит 1 = 0 → переотправить SEQ=1
PC-B получает SEQ=1 → ACK BITMAP=0b1111 (все 4 получены)
PC-A сдвигает окно: WINDOW_BASE=4, отправляет SEQ=4,5,6,7
```

**Когда PC-B отправляет ACK:**
- После каждого принятого кадра (минимальная задержка, подходит для текста)
- Или по заполнению окна (меньше ACK-трафика, подходит для файлов)
- Параметр `ackPolicy: PER_FRAME | PER_WINDOW` — выбирается в конфиге

### Progress bar — как реализовать

Два уровня прогресса одновременно:

```
Подтверждено:  [████████████░░░░░░░░░] 48% ← confirmed_frames / total_frames
В полёте:      [░░░░░░░░░░░░████░░░░░] 56% ← (confirmed + sent_unconfirmed) / total

Кадров: 1250 / 2600   Осталось: ~3.2 с
```

```java
// Расчёт прогресса в Java:
double progress    = (double) confirmedFrames / totalFrames;
double theoretical = (double) sentFrames      / totalFrames;

// Расчёт оставшегося времени (скользящее среднее):
double fps = confirmedFrames / elapsedSeconds; // кадров/сек, обновляем каждую секунду
double etaSeconds = (totalFrames - confirmedFrames) / fps;
```

**Важно:** `confirmedFrames` только растёт — прогресс никогда не идёт назад даже при переотправке.

### При увеличении скорости FSO — нужно ли менять код?

**Нет, если параметры вынесены в конфиг:**

```java
class ProtocolConfig {
    int framePayloadBytes = 249; // байт полезной нагрузки в кадре
    int windowSize        = 4;   // кадров в одном окне
    int ackTimeoutMs      = 400; // 3 × RTT
    int maxRetries        = 3;
    AckPolicy ackPolicy   = PER_FRAME;
}
```

При росте скорости меняется только `windowSize`:

| Скорость FSO | BDP (байт) | Мин. окно | Рекомендуемое |
|---|---|---|---|
| 24 кбит/с (сейчас) | 375 | 2 | **4** |
| 48 кбит/с | 750 | 3 | 6 |
| 100 кбит/с | 1563 | 7 | **8** |
| 1 Мбит/с | 15 625 | 63 | 64 |

Правило: `windowSize = ceil(BDP / framePayloadBytes) × 2` — это одна строка при конфигурировании.

### Почему не использовать весь доступный буфер?

**Уточнение:** 64 KB — это свободная RAM на **STM32**, которую мы не трогаем (STM32 — чёрный ящик). Java-сторона ограничена только heap JVM (сотни MB).

**Предлагаемое разделение буферов в Java:**

| Буфер | Размер | Назначение |
|---|---|---|
| Retransmit window | 4–8 кадров = 2 KB | Хранит отправленные, но не подтверждённые кадры |
| **Outgoing prefetch queue** | **256 кадров ≈ 64 KB** | Файл/сообщение загружается целиком до начала передачи |
| **Incoming reassembly** | **256 кадров ≈ 64 KB** | Сборка входящего файла/сообщения в памяти |
| Voice jitter buffer | 40 кадров ≈ 2.5 с аудио | Сглаживает джиттер канала для голоса |

**Зачем большой prefetch queue:**
- Файл уже в RAM → нет задержек на чтение диска во время передачи
- При burst-потерях очередь не исчерпывается — следующие кадры готовы немедленно
- Скорость ограничивается каналом (3000 байт/с), а не I/O диска

**Retransmit buffer остаётся маленьким** (n×255) — его размер определяется окном, а не объёмом файла. Это принципиальное разграничение: retransmit ≠ prefetch.

## Сводная рекомендация

| Аспект | Выбор | Ключевое обоснование |
|---|---|---|
| Framing | Length-delimited (SOF + LEN + CRC8, poly 0x07) | Простейший, при < 5% потерях sync recovery редкий |
| ACK/NACK | Bitmap ACK, 4 байта | Фиксированный размер, trivially parseable |
| Окно | n = 4 (тексты) / n = 8 (файлы) | BDP = 1.5 кадра, запас × 2–4 |
| Flow control | Credit-based Semaphore в Java | Нет изменений STM32, 15 строк |
| Тестирование | Java FSO Emulator + Virtual COM | TDD без железа |

**Всё реализуется только в Java.** STM32 не трогаем. Никаких библиотек кроме стандартной Java + любой serial port (jssc / jSerialComm).

## Структура пакета (предварительная)

```
[0x7E] [SEQ: 1B] [TYPE: 1B] [LEN: 1B] [PAYLOAD ≤ 250B] [CRC8: 1B]
```

**TYPE:**
- `0x01` DATA
- `0x02` ACK (payload = WINDOW_BASE + BITMAP 2B)
- `0x03` PROBE
- `0x04` PROBE_RESP
- `0x10` FILE_BEGIN (payload = filename, size)
- `0x11` FILE_END
- `0x20` VOICE_SEGMENT

**Итого header:** 6 байт → payload до 249 байт при физическом кадре 255 байт.
