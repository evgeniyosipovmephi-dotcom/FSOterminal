# Дизайн bulk-протокола для передачи файлов

> Статус: 🔵 ПЛАН (дизайн утверждён, реализации пока нет).
> Основан на замерах на железе COM22↔COM25, FSO 24 кбод (раздел 10).
> Все 6 открытых вопросов закрыты (раздел 11).

## 1. Цель и контекст

Сейчас `TYPE_BULK_*` живут только в `SerialLoopbackTest` и тестируют пропускную
способность. Задача — вынести bulk в прод (`protocol/`), чтобы UI мог надёжно
слать **большие файлы** (мегабайты) по FSO-каналу с потерями. Старая концепция
(sliding-window WINDOW=1 + `FileAssembler`) **убирается** — bulk заменяет путь
передачи файлов целиком. Для коротких текстовых сообщений — отдельный лёгкий
механизм (раздел 7).

Ключевые ограничения канала (доказаны замерами):
- FSO = 24000 бод 8N1 = **2400 байт/с** физический потолок.
- STM пакует **каждый USB-кусок ≤64 Б** в отдельный PtPP2-пакет (+10 Б overhead).
  → overhead = `10 × ceil(кадр/64)`, а не 10 однократно.
- Входной буфер STM = 512 Б. Кадр 64 Б → буфер держит **8 кадров** (большая подушка).
- **Только 64-Б кадр можно «передавливать» (over-drive)** — слать быстрее пола,
  буфер сглаживает, потери чистятся дешёвыми ретрансмитами. Кадры ≥128 Б при
  over-drive рушатся в каскад (замер 128@45 = 1055 Б/с ☠).

## 2. Базовое решение: кадр 64 байта

Все DATA-кадры — ровно 64 байта на проводе (1 USB-кусок). Это единственный размер,
дающий и эффективность, и устойчивость к over-drive.

```
Конверт FrameCodec (без изменений):
[SOF 0xAA][SEQ 1][TYPE 1][LEN 1][PAYLOAD = LEN Б][CRC8 1]   overhead = 5 Б
```

## 3. Форматы кадров (payload каждого TYPE)

Номера типов — предварительные (диапазон 0x30–0x3F свободен после удаления старья):

`kind` в FILE_BEGIN: 0=файл, 1=голос, 2=изображение — приёмник так понимает,
как рендерить (превью/плеер). Голос и фото идут тем же bulk, что и файлы.

`tid` (transfer-id, 1 Б, rolling) — есть во всех кадрах передачи. Приёмник на новый tid
сбрасывает недопринятый файл и начинает свежий; кадры с чужим tid игнорирует. Это
защищает от смешивания отменённой и новой передачи (хвосты старой безвредны).

| TYPE | Имя | payload | Назначение |
|---|---|---|---|
| 0x30 | FILE_BEGIN | `[tid 1][kind 1][blocks 2][size 4][nameLen 1][name…]` | старт файла |
| 0x32 | DATA | `[tid 1][blk 1][idx 2][data ≤55]` | данные блока |
| 0x33 | BLOCK_END | `[tid 1][blk 1][count 2]` | конец блока (отпр. повторяет) |
| 0x34 | NACK | `[tid 1][blk 1][count 2][bitmap ceil(count/8)]` | бит=0 → кадр потерян |
| 0x35 | BLOCK_DONE | `[tid 1][blk 1]` | блок собран полностью |
| 0x36 | FILE_END | `[tid 1]` | конец файла (отпр. шлёт ×3) |
| 0x38 | MSG | `[msg_id 1][flag 1][текст ≤57]` | текст (flag 0xFF=ещё / 0x00=последний) |
| 0x39 | MSG_ACK | `[msg_id 1]` | подтверждение текстового фрагмента |

**DATA-кадр (64 Б):**
```
HEADER(4) + [tid 1][blk 1][idx_lo 1][idx_hi 1][data 55] + CRC8(1) = 64
payload(LEN) = 59 Б,  данных = 55 Б
```
- `tid` (1 Б, rolling) — id передачи (защита от смешивания отменённой и новой).
- `blk` (1 Б, mod 256) — номер блока, защищает от «опоздавших» кадров прошлого блока.
- `idx` (2 Б) — номер кадра ВНУТРИ блока (0..count-1).
- Эффективность: 55/74 = 74.3%.

## 4. Блочный ARQ (главное для больших файлов)

Битмап NACK = `кадров/8`. Без блоков для 1 МБ это 2250 Б — не влезает в кадр.
Решение: файл режется на **блоки по K кадров**, каждый блок доводится до конца,
потом следующий (stop-and-wait на уровне блоков).

**Размер блока: K = 400 кадров (~22 КБ).** Замеры (раздел 10) доказали, что размер
блока **на скорость не влияет** (408 и 1500 дали одинаковые 1637–1684 Б/с). Поэтому
выбран по другим критериям:
- NACK при K ≤ 432 → битмап ≤54 Б → кадр ≤64 Б = **1 USB-кусок** (все управляющие
  кадры 1-кусковые, нет особых случаев).
- Готовый блок сразу дописывается в файл → память приёмника ограничена ~22 КБ,
  передача 100 МБ не упирается в RAM.
- Плавный прогресс-бар, частые точки восстановления.

**Поток передачи блока:**
```
Отпр: BLOCK_BEGIN(blk, n) → [n DATA-кадров, с пейсингом] → BLOCK_END(blk, n)
Прм:  на BLOCK_END → собрать bitmap → есть потери? NACK(blk, n, bitmap)
                                       нет потерь?  BLOCK_DONE(blk)
Отпр: на NACK → ретрансмит потерянных DATA → BLOCK_END снова → (цикл)
       на BLOCK_DONE → блок готов → BLOCK_BEGIN(blk+1)
```

**Завершение файла:** после `BLOCK_DONE` последнего блока отпр. шлёт `FILE_END`
(×3, идемпотентно). Приёмник на FILE_END финализирует файл.

## 5. Надёжность управляющих кадров

Опасность — потеря END/NACK/DONE/FILE_END приводит к залипанию. Правило:
**один драйвер повтора (отправитель по таймауту), не оба** (иначе шторм).

- Отпр. послал `BLOCK_END`, ответа нет за `endTimeoutMs` → **повторить END**.
- Прм. на каждый (в т.ч. повторный) `BLOCK_END` → отвечает свежим `NACK`/`BLOCK_DONE`.
- Потерян NACK/DONE → придёт повторный END → прм. снова отвечает. Самовосстановление.
- `FILE_END` — «проблема двух генералов»: отпр. шлёт 2-3 раза, прм. идемпотентен.
- `FILE_BEGIN` — надёжный: отпр. повторяет, пока не пойдут NACK/DONE (= прм. готов).
- Лимит повторов END без прогресса (`bulkMaxRetries`) → считать канал разорванным
  (связать с логикой PROBE/disconnect).

## 6. Пейсинг (задержка между DATA-кадрами)

Считаем **пол** передачи кадра по FSO и вычитаем настраиваемый over-drive:
```java
fsoBytes  = кадр + 10 * ceil(кадр / 64);            // PtPP2 на каждый USB-кусок
floorMs   = fsoBytes * 10.0 / 24000 * 1000;
delayMs   = max(0, floorMs - overdriveMs);          // overdriveMs из настроек
// защита: over-drive (delay < floor) разрешён ТОЛЬКО при chunks == 1 (кадр ≤64 Б)
if (chunks > 1) delayMs = ceil(floorMs * 1.10);     // большой кадр — только безопасно
```
Для кадра 64 Б: floor 31 − overdrive 11 = **20 мс** (подтверждённый оптимум).

- Пейсятся **только DATA** (поток). Управляющие кадры (END/NACK/DONE/MSG) — сразу.
- Каждый кадр пейсится по СВОЕМУ размеру (короткий хвостовой кадр — меньший floor).
- **Короткие кадры (< 56 данных) спец-обработки не требуют:** < 64 Б = всё равно
  1 USB-кусок, уже эффективен. Padding до 64 НЕ нужен.

**Реализация пейсинга:** выделенный фоновый поток-отправитель + `Thread.sleep(delayMs)`
между кадрами + **приоритетная очередь** (чтобы текстовый MSG обгонял кадры файла).
Поток фоновый → JavaFX-поток не блокируется.

## 7. Короткие текстовые сообщения (отдельная лёгкая дорожка)

Файл 1 МБ льётся ~10 мин и монополизирует канал. Чтобы чат жил во время передачи,
текст идёт **мимо** блочного ARQ — лёгким механизмом:

```
MSG      [msg_id 1][flag 1][текст UTF-8 ≤57]   flag: 0xFF — ещё фрагмент, 0x00 — последний
MSG_ACK  [msg_id 1]
```
- **Надёжность:** stop-and-wait — отпр. шлёт MSG, ждёт `MSG_ACK[msg_id]`, по таймауту
  повторяет. `msg_id` (rolling 1 Б) → приёмник отбрасывает дубликат при потере ACK.
- **Фрагментация длинного текста:** байт `flag` — это готовый механизм. Длинный текст
  режется на MSG-кадры (≤57 Б ≈ 28 кирилл. символов), приёмник склеивает до `flag=0x00`.
  **Переиспользуем логику `TextAssembler`** (он уже собирает по флагу 0xFF/0x00).
  Третий протокол не нужен.
- **Приоритет:** MSG-кадр вставляется в очередь отправки ПЕРЕД кадрами файла; файл
  пейсится с зазорами ~20 мс — MSG проскакивает в зазор, файл задержится на ~30 мс.
- Приёмник маршрутизирует по TYPE: MSG не попадает в битмап блока, не ломает счёт файла.

## 8. Настройки (`ProtocolConfig`, в меню «Параметры протокола…»)

| Ключ | По умолч. | Описание |
|---|---|---|
| `bulkOverdriveMs` | 11 | насколько слать быстрее пола (0 = безопасно по полу) |
| `bulkBlockFrames` | 400 | кадров в блоке (NACK = 1 USB-кусок при ≤432) |
| `bulkEndTimeoutMs` | 400 | таймаут ожидания NACK/DONE перед повтором END |
| `bulkMaxRetries` | 10 | повторов END без прогресса → разрыв |

`bulkFramePayload` (56) держим константой — привязан к 64-Б выравниванию.

## 9. Структура классов (чистая Java, без JavaFX)

```
protocol/
├── BulkSender.java    — гонит файл/byte[]: блоки, пейсинг, ретрансмит по NACK, таймауты
│                        вход: источник данных, frameOutput (Consumer<byte[]>), config
│                        выход: callback прогресса
├── BulkReceiver.java  — feed(frame): сборка блоков, дозапись в файл, отправка NACK/DONE
│                        выход: callback прогресса + завершения
├── MsgChannel.java    — лёгкий текст: MSG/MSG_ACK, stop-and-wait, приоритет (раздел 7)
```
- Пейсинг — выделенный поток + `Thread.sleep` + приоритетная очередь (раздел 6).
- UI подключает BulkSender/Receiver к `SerialChannel` для функции 📎 (заменяет
  `FileAssembler`).
- Юнит-тесты на `FSOEmulator` (без железа) + интеграционный на COM-портах.

## 10. Замеры, на которых основан дизайн (чистый канал)

**Подбор кадра/задержки (100 КБ):**

| Кадр | Задержка | Throughput | Раундов | Ретрансм. | Вывод |
|---|---|---|---|---|---|
| 64 (data 57) | 20 мс | **1672–1708** | 4 | 26% | оптимум (over-drive) |
| 64 (data 57) | 28 мс | 1587 | 4 | 15% | компромисс |
| 64 (data 57) | 35 мс | 1542 | 2 | 2.6% | безопасно |
| 128 (data 121) | 45 мс | 1055 ☠ | 9 | каскад | over-drive рушит |
| 128 (data 121) | 70 мс | 1515 | 2 | 4.3% | только безопасно |

Потолок для 64-Б кадра = 1849 Б/с; 20 мс даёт 90% от него.

**Размер блока (256 КБ, кадр 56, задержка 20 мс):**

| Направл. | Блок | Время | Скорость | NACK | Раундов |
|---|---|---|---|---|---|
| A→B | 1500 | 159.6 с | 1642 | 4 куска | 11 |
| A→B | 408 | 160.2 с | 1637 | 1 кусок | 27 |
| B→A | 1500 | 155.7 с | 1684 | 4 куска | 8 |
| B→A | 408 | 155.8 с | 1683 | 1 кусок | 24 |

→ **Размер блока на скорость не влияет** (разница 0.3%, в пределах шума).
Направление влияет сильнее (~3% асимметрия канала). Поэтому блок выбран = 400
по чистоте NACK и памяти, а не по скорости.

## 11. Решения (закрытые вопросы)

1. **blk в DATA:** ✅ да, 1 Б (data=56). 1 байт дешевле редкого, но злого бага на
   границе блоков.
2. **Размер блока:** ✅ **400 кадров.** Замерами доказано — на скорость не влияет;
   400 даёт 1-кусковый NACK + малую память + плавный прогресс.
3. **FILE_BEGIN/END:** ✅ новые типы (0x30/0x36). Старую концепцию (sliding-window,
   FileAssembler) убираем целиком.
4. **Сосуществование:** ✅ bulk **заменяет** передачу файлов. Короткий текст — отдельная
   лёгкая дорожка MSG/MSG_ACK с приоритетом над файлом (раздел 7).
5. **Источник пейсинга:** ✅ выделенный поток + `Thread.sleep` + приоритетная очередь.
6. **CRC файла:** ✅ не нужен. Целостность уже гарантируют PtPP2 **CRC32** (на FSO) и
   аппаратная CRC USB; битый кадр не доходит до нашего CRC8 — отваливается как «потеря»
   и уходит в ретрансмит. CRC8 нужен только для ресинхронизации. `FILE_END` пустой.
